# Design reference router

Read the guide that matches the design task. Do not use one reference stack for
every kind of design. Each guide is an on-demand SKILLS-type document; copy into an
adopting project only the guides for the kinds of design it does.

| Task | Guide |
|---|---|
| Product apps, SaaS, desktop tools, dashboards, editors, views, components, interactions | [UI design guidance](../ui-design-guidance.md) |
| Game HUDs, menus, inventories, match setup, game UX | [Game UI and HUD](game-ui-hud.md) |
| Landing pages, marketing sites, product websites | [Landing and marketing web](landing-marketing-web.md) |
| Logos, identity systems, brand marks, favicons | [Brand and identity](brand-identity.md) |
| Posters, editorial, typography, visual campaigns, general graphic design | [Graphic and visual design](graphic-visual-design.md) |

A task can span guides: a game's settings screen uses the game guide for visual
language and the UI guidance for control behavior.

## Shared guidance

- **Reference before inventing.** Browse strong examples before substantial design work.
- Prefer excellent real-world work over generic AI concepts.
- Look at multiple relevant references; synthesize rather than copy.
- Preserve project-specific requirements and existing visual language.
- Novel functionality does not automatically require novel controls or visual conventions.
- When a conventional solution exists, understand it before deviating from it.
- Judge design in context: hierarchy, density, legibility, states, interaction,
  content, and surrounding UI, not isolated prettiness.
- When unsure, research instead of guessing.

Source access, citation honesty, and the exemptions for small fixes and prototypes
in the [UI design guidance](../ui-design-guidance.md) apply to every guide.
