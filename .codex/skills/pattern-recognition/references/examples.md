# Decision examples

**Purpose:** Show how pattern recognition changes the engineering decision.

**Constraints:** These are worked scenarios, not reports of tests or grants of access. Project contracts determine actual behavior and verification.

| Observation | Decision to examine | Useful completion evidence |
|---|---|---|
| A completed update is rebuilt after restart preparation fails | Build completion and apply failure are independent facts. Trace the artifact through check, failure, restart and retry before adding another status guard. | Exact target and bytes remain reusable; failed attempt evidence survives; stale or changed artifacts are refused. |
| A coordinated save says only that some window did not respond | Separate missing acknowledgement, active work, an explicit failure and a stalled participant. Repair collection at the coordinating owner. | A request identifies each window, pending work and result without capturing user content. |
| An old install failure appears in a later status reply | Refresh installed identity and required service records before deciding whether delivery is still blocked. | The report names current observed state and separately dates historical failures. |
| The agent wants screenshots to learn whether an editor shows unsaved work | Ask the owner about that visible condition. State a high-value and unique purpose before proposing Computer Use. | The needed fact is obtained with proportionate effort and within actual permission. |
| One instance of a retained view silently replaces another save callback | Identify registrations by instance rather than display label. Find every caller of the same lifecycle owner. | Both instances preserve their own content and report their save outcomes. |

The skill's procedure applies across these examples. It does not prescribe a particular
updater, UI framework, timeout, process-management command or storage layout.
